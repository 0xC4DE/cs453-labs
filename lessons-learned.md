# CS 553: Lessons Learned for undergraduates or first-time creators

When building a web application, particularly using Javascript, there are multiple considerations that one must make. These decisions include but are not limited to: technical design, database design, authentication, authorization, and future expandability. The most important of which would probably be the technical design of the overall application. This is doubly important for a microframework like Express.js, since it allows you to modify any part of the request flow at any time. The actual meaning of technical design in this context is simply where certain functions will livei. For example, having CRUD functions strictly in one file, having all authentication in another and authorization in a third. This is done for strict segmentation, but comes with trade-offs, especially in inter-operability and how easy each component is to expand. This goes along with considering your database design, authentication, and authorization early because all three of those work closely together to deliver something. The only real trade-off with this segmented design is that it does increase the complexity of the codebase, which is something I encountered meaning as I expanded more and more it became more cumbersome to expand. This is a general symptom of a light tech debt and not generalizing enough.

Here's a relatively practical example: A user authenticates, which reaches a get_user function against the database, part of the CRUD. Then, the end-user uses that User information inside of a reqeuest. The application would then need to verify both that the user passed-in is valid AND that the user is authorized to perform this action, in that order. This already touches the database twice more. Consider there may be a dozen or more of these endpoints that need to be able to follow the flow of: get a user, verify the user, verify the user's access, and it should be readily apparantly that keeping these specific, segmented, and concise are important functions.

I made the mistake of not segmenting early enough, and it caused me to have to refactor endpoints several times and split things out into validation middleware functions and service functions, which are essentially CRUD functions. My specific piece of advice for anybody building a service like this would be to plan segmentation early, segment the code early, and repeatedly revisit the sections of code in which are seggmented so that they can be. This is also exactly the advice I would follow if I were rebuilding this project from scratch. Additionally, I would strongly recommend people make use of software like an Object-Relational Mapping (ORM) library to make all CRUD operations much cleaner and the overall codebase much more programmatic instead of writing raw SQL queries in a file, which can get convoluted, annoying to maintain, and be just hard to read.

Finally, a huge security risk to a system like this is naturally the openness of the API. Making sure your Authentication and Authorization system are fully airtight is something that should be on the forefront of anybody's mind who is building an API system such as this. Naturally, should somebody have incorrect authentication things like account spoofing and session stealing are very prevalent. Similarly, if authorization is wrong somebody can access resources they have no reason to access in the first place. These are very common issues that are seen in several projects, and it should be heavily considered whether or not those element are instrumental to your application. There are several design challenges web APIs like this face and several of them can be worked around and improved, it is important to consider all of the elements before you begin work so that you can organize things appropriately and make design decisions that make sense instead of guessing.
